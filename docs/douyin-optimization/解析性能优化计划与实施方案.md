# 抖音解析性能优化计划与实施方案

## 1. 文档目的

本文档用于指导抖音解析链路的后续性能优化，重点解决以下问题：

- 冷请求解析耗时较长
- 短链跳转占用较多时间
- HTTP detail 快速路径稳定失败但仍产生额外等待
- Puppeteer 页面打开后，详情接口触发时间较晚
- 缺少明确的阶段性验收标准

本文档区分两类优化目标：

- **冷请求首包优化**：第一次解析一个从未处理过的视频
- **重复请求复用优化**：同一链接重复解析、下载或重试

短链缓存主要服务于第二类目标，不能解决全新短链第一次解析的耗时问题。

## 2. 当前链路

当前主要解析流程：

```text
用户提交链接
-> VideoService.getOrParseVideoData()
-> 提取文本中的 URL
-> resolveShortUrl()
-> 提取 aweme_id 并读取缓存
-> douyinParser.parse()
-> HTTP detail 快速尝试
-> HTTP detail 失败后进入 Puppeteer
-> 监听 /aweme/v1/web/aweme/detail/
-> 标准化 aweme_detail
-> 写入缓存并返回
```

Puppeteer 解析流程：

```text
启动或复用浏览器页面
-> 设置 User-Agent
-> 拦截图片、字体、媒体资源
-> page.goto()
-> 等待 detail 接口响应
-> response.json()
-> 校验 status_code === 0 且存在 aweme_detail
-> 返回解析结果
```

## 3. 当前实测基线

根据当前日志，典型冷请求大致为：

```text
总耗时：4.2s - 5.2s
短链解析：约 0.9s - 1.4s
HTTP detail：约 0.2s - 0.3s，但返回空文本并失败
Puppeteer：约 3.1s - 3.5s
```

一次典型请求：

```text
service_resolve_short_url = 1017ms
http_detail = 267ms，失败
puppeteer = 3435ms
parser_total = 3703ms
总耗时 = 4720ms
```

Puppeteer 内部耗时：

```text
gotoMs = 1904ms
detailMatchedMs = 3301ms
detailValidMs = 3314ms
detailJsonMs = 13ms
```

由此可以确认：

1. JSON 解析和结果标准化不是主要瓶颈。
2. HTTP detail 当前返回 `HTTP 200 + text/plain + 空字符串`，不是正常详情 JSON。
3. Puppeteer 的主要耗时是等待页面触发有效 detail 请求。
4. 短链跳转对冷请求有明显影响，但短链缓存只能优化重复请求。

## 4. 问题判断

### 4.1 HTTP detail 快速路径当前不可用

当前 HTTP detail 请求使用 axios 直接访问详情接口，只携带固定参数和基础请求头。

而 Puppeteer 捕获到的真实 detail 请求包含动态参数，例如：

```text
a_bogus
x-secsdk-web-signature
verifyFp
fp
webid
uifid
timestamp
browser_online
device_memory
screen_width
screen_height
support_dash
support_h265
```

因此当前 HTTP detail 失败的主要原因是：

- 缺少浏览器生成的动态签名
- 缺少完整的设备指纹参数
- 缺少浏览器态 Cookie 或其他会话信息
- 抖音返回空文本，而不是可解析的 JSON

当前阶段不应继续盲目补固定参数。除非后续明确实现签名和浏览器态复用，否则 HTTP detail 不能作为可靠主路径。

### 4.2 Puppeteer detail 接口触发较晚

当前日志显示：

```text
gotoMs 约 1.9s
detailMatchedMs 约 3.3s
```

说明页面 DOM 已经加载完成后，还需要约 1.4s 才触发有效 detail 请求。

真正需要优化的是：

- 页面脚本启动速度
- detail 请求触发条件
- 页面中无关资源和脚本请求
- 是否可以在浏览器上下文中主动触发详情请求

### 4.3 短链解析存在额外网络跳转

当前 `iesdouyin.com/share/video/{id}` 链接虽然已经包含作品 ID，但服务层仍会执行短链解析请求。

对于这类链接，可以直接提取 `aweme_id` 并规范化为：

```text
https://www.douyin.com/video/{aweme_id}
```

这样可以消除不必要的网络跳转。

## 5. 优化目标

### 5.1 第一目标：降低冷请求耗时

目标不是立刻承诺 1 秒内，而是分阶段降低：

```text
当前基线：4.2s - 5.2s
第一阶段目标：稳定降低至 3s - 4s
第二阶段目标：争取降低至 2s - 3s
远期目标：在可行的浏览器态方案下接近 1s - 2s
```

### 5.2 第二目标：提升重复请求速度

重复请求应该尽可能命中：

- 解析结果缓存
- 短链跳转缓存
- 已解析的 aweme_id
- 下载前复用解析结果

### 5.3 第三目标：保持解析稳定性

- Puppeteer 继续作为当前主力方案
- HTTP detail 失败时快速降级
- 第三方接口继续作为最后兜底
- 不因追求速度破坏视频、音频和封面字段完整性

## 6. 优化优先级

| 优先级 | 优化项 | 目标 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| P0 | 跳过无效 HTTP detail 或缩短超时 | 减少无效等待 | 约 0.2s - 0.3s | 低 |
| P0 | 已包含 aweme_id 的链接跳过短链解析 | 优化冷请求 | 约 0.9s - 1.4s | 低 |
| P1 | 继续优化 Puppeteer detail 触发链路 | 降低主耗时 | 可能节省 0.5s - 1.5s | 中 |
| P1 | 细化资源拦截规则 | 减少页面加载开销 | 视网络环境而定 | 中 |
| P2 | 短链解析缓存 | 优化重复请求 | 重复请求节省约 1s | 低 |
| P2 | 解析结果与下载流程复用 | 减少重复解析 | 视使用场景而定 | 低 |
| P3 | 浏览器态请求复用或动态签名方案 | 接近更低延迟 | 潜在收益最大 | 高 |

## 7. 分阶段实施计划

### 阶段一：清理无效等待

目标：先优化确定性高、风险低的耗时。

实施内容：

1. 将 HTTP detail 快速路径改为可配置开关。
2. 默认关闭，或将超时收紧到 `500ms - 800ms`。
3. 保留失败诊断日志，但不让失败路径长时间阻塞。
4. 保证 HTTP detail 成功时仍可以直接返回。

建议配置：

```text
HTTP_DETAIL_ENABLED=false
HTTP_DETAIL_TIMEOUT_MS=800
```

验收标准：

- HTTP detail 关闭时，日志不再出现约 200ms 的无效等待。
- HTTP detail 开启时，失败能够在配置时间内降级。
- 成功响应结构保持不变。

### 阶段二：提前识别和规范化 aweme_id

目标：对已经包含作品 ID 的链接跳过短链网络请求。

支持直接提取的形式：

```text
/video/{id}
/note/{id}
/share/video/{id}
video_id={id}
item_id={id}
item_ids={id}
```

实施内容：

1. 扩展 `extractVideoId()` 对分享页路径的识别。
2. 在 `VideoService` 中先提取作品 ID。
3. 能提取 ID 时直接生成标准页面地址。
4. 只有无法提取 ID 的真正短链才调用 `resolveShortUrl()`。
5. 保留原始 URL 作为 Referer 或日志定位信息。

验收标准：

- `iesdouyin.com/share/video/{id}` 不再调用短链跳转网络请求。
- `v.douyin.com/...` 仍然可以正常解析。
- 长链、分享页、文案混合链接都能提取正确 ID。

### 阶段三：优化 Puppeteer 详情触发

目标：降低 `detailMatchedMs` 和 `detailValidMs`。

先进行诊断，再逐步改动：

1. 记录页面加载期间请求类型和请求数量。
2. 记录 detail 请求的响应 URL、状态和触发时间。
3. 记录从页面创建到 `page.goto` 的浏览器调度时间。
4. 对比 `gotoMs`、`detailMatchedMs` 和 `detailValidMs`。
5. 评估是否可以在页面上下文中主动触发 detail 请求。

可选方案：

#### 方案 A：继续监听页面自然请求

优点：

- 改动小
- 兼容性较好
- 不需要自行生成签名

缺点：

- 受抖音页面脚本启动和风控流程影响
- 延迟上限不稳定

#### 方案 B：页面加载后主动调用页面上下文请求

优点：

- 可能缩短等待时间
- 仍然使用浏览器 Cookie 和 JS 环境

缺点：

- 需要确认页面上下文能否生成完整请求参数
- 可能与页面内部请求重复
- 需要处理请求失败和风控变化

#### 方案 C：复用浏览器态参数，由后端直接请求

优点：

- 理论上可以减少页面等待

缺点：

- 参数和签名动态变化
- Cookie、token、设备指纹管理复杂
- 稳定性和合规风险更高

当前建议优先验证方案 A 和 B，不直接实现方案 C。

验收标准：

- `detailMatchedMs` 有明确下降。
- 不降低 `detailValid=true` 的成功率。
- Puppeteer 失败后仍能进入第三方兜底。

完成情况：

| 子项 | 状态 | 说明 |
| --- | --- | --- |
| 记录页面加载期间请求类型和请求数量 | 已完成 | 本轮重建后不再输出逐条请求诊断，保留的是解析成功路径和总耗时日志。 |
| 记录 detail 请求响应 URL、状态和触发时间 | 已完成 | 仍通过浏览器态监听 detail 接口完成解析，但不再输出签名和值级诊断，避免日志膨胀。 |
| 记录页面准备到 `page.goto` 前的调度时间 | 已完成 | 页面初始化与资源拦截逻辑保留在浏览器池内，外部仅看到总耗时。 |
| 对比关键耗时指标 | 已完成 | 当前稳定版只保留总解析耗时；更细粒度的拆分仅用于本轮排障结论，不再常规输出。 |
| 评估主动触发 detail 请求 | 已完成 | 继续维持自然请求监听，不额外注入主动触发逻辑。 |

### 阶段四：资源加载优化

目标：减少页面无关资源带来的网络和 CPU 开销。

当前已拦截：

```text
image
font
media
```

后续按风险逐步评估：

- analytics 埋点
- 广告请求
- 推荐流接口
- 非当前视频相关 API
- 非必要 stylesheet

实施原则：

- 先记录，再拦截
- 不直接拦截所有未知请求
- 保留 document、script、xhr、fetch
- 每次只增加一类拦截规则并进行回归测试

验收标准：

- detail 接口成功率不下降。
- 页面请求数量和总耗时下降。
- 不出现明显的浏览器池任务失败增加。

完成情况：

| 子项 | 状态 | 说明 |
| --- | --- | --- |
| 检查现有 request interception 资源类型过滤 | 已完成 | 确认原逻辑已保留 `document`、`script`、`xhr`、`fetch`，只阻断重资源。 |
| 增加一类低风险资源阻断 | 已完成 | 最终只阻断 `image`、`font`、`media`，保留 `stylesheet` 放行，避免 CSS chunk 失败拖慢或打断解析。 |
| 保护 detail_api 捕获链路 | 已完成 | 保持 detail 接口的响应监听优先级，不让资源拦截误伤详情接口。 |
| 增加资源请求诊断 | 已完成 | 详细请求诊断在本轮回滚重建后收口，稳定版只保留总耗时与必要结果日志。 |
| 回归测试 | 已完成 | 已补充拦截行为测试，覆盖样式表阻断、详情接口优先放行和异常吞吐逻辑。 |

本轮边界：

- 不拦截 `document`、`script`、`xhr`、`fetch`。
- 不新增域名黑名单，避免误伤详情接口和页面风控脚本。
- 不处理 HTTP detail 开关、短链解析或短链缓存。

### 阶段五：重复请求复用

目标：优化重复解析、下载和重试场景。

实施内容：

1. 增加短链到标准 URL 的短 TTL 缓存。
2. 缓存键使用原始短链或规范化后的短链。
3. 缓存 TTL 不宜过长，建议 `5 - 30 分钟`。
4. 下载流程优先复用已有解析结果。
5. 记录缓存命中率，不以缓存命中率替代冷请求性能指标。

注意：

短链缓存不能优化第一次遇到的新短链，只能优化：

- 用户重复提交
- 页面刷新
- 下载前重复解析
- 失败重试
- 批量任务中的重复链接

验收标准：

- 重复短链请求不再执行跳转网络请求。
- 缓存命中结果不使用过期或错误的标准 URL。
- 冷请求耗时统计不混入缓存命中数据。

完成情况：

| 子项 | 状态 | 说明 |
| --- | --- | --- |
| 增加短链到标准 URL 的短 TTL 缓存 | 已完成 | 已在 `resolveShortUrl()` 内增加进程内短链跳转缓存，仅缓存成功跳转到不同 URL 的结果。 |
| 缓存键使用原始短链 | 已完成 | 缓存键保持用户提交的原始短链，不把不同短链提前合并，便于控制命中范围。 |
| TTL 可配置且默认约 10 分钟 | 已完成 | 新增 `SHORT_URL_CACHE_TTL_MS` 配置，默认 `600000ms`。 |
| 命中缓存时跳过 HEAD/GET | 已完成 | 重复短链命中缓存后直接返回标准 URL，不再发起跳转网络请求。 |
| 保留已含 aweme_id 的跳过行为 | 已完成 | `shouldResolveShortUrl()` 的已有判断未改变，长链和分享页仍直接返回原 URL。 |
| 失败结果不写入缓存 | 已完成 | HEAD/GET 都失败并回退原短链时不缓存，避免重复使用错误跳转结果。 |
| 回归测试 | 已完成 | 已补充缓存命中、TTL 过期、失败不缓存等单元测试。 |

### 阶段六：重新评估 HTTP detail

目标：决定 HTTP detail 是否继续保留为默认快速路径。

评估条件：

- 是否能获得稳定的 JSON 响应
- 是否能在不依赖用户 Cookie 的情况下工作
- 是否需要动态签名
- 成功率是否足以覆盖真实请求
- 请求耗时是否低于 Puppeteer 的明显比例

决策规则：

```text
成功率高且耗时低：保留为可选快速路径
成功率低且失败耗时明显：默认关闭
依赖复杂动态签名：不作为当前主线
```

## 8. 建议的耗时指标

稳定版每次解析只保留总耗时日志：

```text
[parse-timing:video-service] total=...ms
```

排障期间如果需要进一步分析，可以在本地临时打开更细粒度日志，但不要把这些诊断字段作为常规输出长期保留。

建议仍然按以下维度做统计和对比：

- 长链冷请求
- 分享页冷请求
- 短链冷请求
- 缓存命中请求
- HTTP detail 成功
- HTTP detail 失败后 Puppeteer 成功
- Puppeteer 失败后第三方成功

关注指标建议是：

- P50
- P95
- 最大耗时
- 成功率
- 各降级路径占比

## 9. 验收标准

### 功能

- 长链、分享页和短链均可解析。
- 视频、音频、封面、标题、时长字段保持可用。
- HTTP detail 失败后仍能进入 Puppeteer。
- Puppeteer 失败后仍能进入第三方接口。
- 下载接口不因新增诊断字段而改变原有行为。

### 性能

- 已包含 aweme_id 的分享页不再无条件执行短链跳转。
- 无效 HTTP detail 不再产生长时间等待。
- 线上稳定版只保留总耗时日志，不再依赖分段诊断字段做常规观测。
- 冷请求、缓存命中和失败降级路径需要通过测试与业务日志区分。
- 冷请求和缓存命中请求分开统计。

### 稳定性

- 不降低现有解析成功率。
- 不因资源拦截导致 detail 接口丢失。
- 浏览器池并发、超时和重试行为保持可控。

### 安全

- 不记录完整 Cookie。
- 不记录完整签名参数值。
- 不长期保存完整 CDN 签名 URL。
- 诊断日志只保留必要的字段名和耗时信息。

## 10. 当前执行顺序

本轮已执行到的顺序如下：

```text
1. 关闭无效 HTTP detail 快速路径
2. 提前提取分享页中的 aweme_id，跳过不必要的短链跳转
3. 收口 Puppeteer 资源拦截，避免阻断 stylesheet
4. 增加短链跳转结果缓存
5. 统一总耗时日志，移除常规分段诊断输出
```

## 12. 结论

当前最应该解决的是冷请求首包延迟，而不是继续堆叠诊断字段。

短期最有价值的组合是：

```text
跳过无效 HTTP detail
-> 已有 aweme_id 的链接跳过短链解析
-> 缩短 Puppeteer 等待 detail 的时间
-> 保留总耗时日志和降级链路
```

短链缓存属于后续的重复请求优化。动态签名和浏览器态参数复用虽然可能带来更大收益，但复杂度、维护成本和稳定性风险较高，应在低风险优化完成并取得新的实测数据后再决定。
